# Автопилот запасов

## Как запустить

Распакуйте архив на компьютере с Python 3.9 или новее. В Windows дважды нажмите start.bat. На macOS и Linux откройте терминал в папке проекта и выполните `python3 app.py`. Дополнительные пакеты не нужны. Откроется страница http://127.0.0.1:8765. Если браузер не открылся автоматически, откройте этот адрес вручную.

В учебном режиме включается отдельная локальная CRM. Сервис читает её по HTTP, рассчитывает партии, отправляет задания обратно и получает подтверждения. Учебная CRM резервирует отправленный товар, отражает входящие перемещения и закрывает распределённую поставку. Журнал на странице обновляется сам. При повторной проверке появится ноль новых заданий: решения уже исполнены в учебной системе. Принятое задание означает регистрацию распоряжения, физическая доставка не моделируется. История учебных продаж фиксирована.

Закрытие вкладки не останавливает процесс. Чтобы остановить сервис, нажмите Ctrl+C в окне программы. Для круглосуточного использования нужен постоянно работающий компьютер или сервер. После перезапуска используется прежняя база SQLite рядом с программой. Чтобы повторить демонстрацию с нуля, остановите программу и удалите только demo.sqlite.

## Как сменить снимок учебной CRM

Остановите сервер и запустите `python3 app.py --snapshot crm-data/01-baseline.json`. Можно выбрать любой из шести файлов в папке `crm-data`. В Windows команду можно начать с `py -3` вместо `python3`. Каждый снимок и его журнал сохраняются в отдельной базе `demo-*.sqlite`. Для чистого повторного прогона используйте свежую копию папки без этих баз. Порядок действий и ожидаемые результаты приведены в [общем описании проекта](../README.md).

## Что рассчитывается

Перемещение сохраняет запас под прогнозный спрос у отправителя. Объём ограничен дефицитом у получателя и продажами, которые успеют произойти после доставки. Модель предполагает, что излишек у отправителя продастся после уценки. Выигрыш партии равен разнице между полной ценой у получателя и будущей ценой у отправителя, умноженной на количество, за вычетом перевозки. Прогнозная дневная скорость и входящие остатки в этом прототипе считаются доступными на всём горизонте. Маршруты выбираются последовательно по максимальному положительному эффекту.

Первая поставка нового сезона распределяется с нуля по заявленному перечню магазинов. Используется статистическая модель спроса. Для соответствующего сезона и товарной группы с размером она суммирует продажи и дни наличия каждого магазина. Скорость продаж магазина сглаживается семью условными днями со средней скоростью сети. Модель заново оценивает параметры по актуальной истории при расчёте каждой новой партии. Целые единицы распределяются пропорционально оценённому спросу, остаток от округления — по наибольшим дробным частям. Если подходящих продаж нет, используется равномерное распределение. Закрытые партии не перепланируются. История перемещений сама по себе не считается спросом.

## Подключение сети

Требуется адаптер учётной системы с контрактом ниже. Сторонняя CRM должна предоставить историю продаж, а ERP или WMS — свободные остатки и исполнение заданий, если этих функций нет в CRM. Укажите CRM_URL и при необходимости CRM_TOKEN в переменных окружения и запустите `python3 app.py --live --no-browser`. Период проверки по умолчанию 900 секунд. Для другого периода используйте `--interval 300`. Панель слушает только локальный интерфейс. Используйте один активный процесс на одну сеть.

GET /snapshot отдаёт согласованный JSON. Полный пример в snapshot.example.json. version — уникальная строка ревизии, одинаковая при неизменных данных. inventory — свободный остаток stock, подтверждённые входящие incoming, ожидаемый суточный спрос rate, дни до скидки days_left, полная цена price и скидка discount от 0 до 1 по артикулу с размером и магазину. Любые входящие за пределами горизонта должны быть исключены адаптером. routes содержит направленные тарифы и сроки. history содержит фактически проданные единицы и число дней наличия за аналогичный сезон, без дублирования периодов. arrivals содержит открытые новые партии с уникальными batch_id и доступными магазинами.

POST /orders получает один JSON вида transfer или allocation. Поля и примеры в orders.example.json. Заголовок Idempotency-Key идентифицирует задание. Адаптер должен атомарно проверить доступный остаток или состояние новой партии, зарегистрировать распоряжение и его ключ. При повторе ключа нужно вернуть уже записанный результат. Положительный ответ — {"accepted":true,"id":"ключ из заголовка"}. Это подтверждение регистрации. Следующий согласованный снимок отражает резерв, входящие товары или закрытие новой партии и их ключи в applied_ids. В этой версии адаптер сохраняет полный журнал применённых ключей. Все запросы используют Bearer-токен, если он задан.

Исходящие задания сохраняются в SQLite до отправки. При недоступности CRM или потере ответа сервис повторяет обмен с тем же ключом. Пока предыдущие задания не отражены в снимке, новые решения не создаются. Некорректные данные и ошибки обмена попадают в журнал. Прототип не разрешает постоянные конфликты остатков автоматически: для промышленного внедрения нужны протокол отмены/перепланирования и мониторинг зависших заданий.

## Как проверить коммерческий эффект

Для пилота сравните магазины с сопоставимыми продажами, ассортиментом и сроками уценки. Сначала сохраните прогнозы без отправки реальных распоряжений и проверьте их на отложенном сезоне, используя лишь данные, доступные к моменту каждой рекомендации. Сравните сезонное распределение с действующим правилом сети. Основные показатели — доля начального запаса, проданного без скидки, расходы на перемещения на единицу товара и фактический прирост валовой прибыли после доставки. Эффект на экране — прогноз при заданных допущениях. Цель первого пилота — плюс 5 процентных пунктов к доле продаж без скидки за 8 недель и положительный финансовый эффект. Для платного запуска понадобится адаптер первого клиента, проверка качества данных и результат пилота.
